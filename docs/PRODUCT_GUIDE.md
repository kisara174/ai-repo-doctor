## 1. 产品承诺

用户给出一个 Python 仓库，Repo Doctor 应当帮助他定位值得检查的代码，展示结构与影响路径，生成有源码证据的诊断，留下可阅读的 issue 报告，并记录修复前后的验证结果。用户始终能分清**程序确认的事实**、**模型提出的假设**和**测试或人工确认的结论**。

产品的最小闭环是：

```text
仓库路径 → 本地结构报告 → 选择一个符号或静态问题
        → 有界上下文与可选云端诊断 → 来源证据校验
        → 带稳定 ID 的 issue → 人工决定和修改
        → 显式运行同一回归检查 → 更新 issue 状态与最终报告
```

基础版 v0.2.0 已把**一个 issue 从发现走到复查**做完整。整仓自动发现所有行为缺陷、自动修改代码和通用准确率承诺属于后续里程碑。

## 2. P0 开始前的基础与缺口

下表保留制定 P0 工作清单时的基线；所列缺口已由 P0-1 至 P0-4 解决。当前未完成的诊断质量工作见第 5 节。

| 环节 | 当时已有 | 当时的闭环缺口 |
| --- | --- | --- |
| 仓库结构 | Python 文件、符号、导入、静态调用、Click 注册、重导出、影响分析 | 可保存且能指向下一步的仓库报告；可搜索目标符号 |
| 诊断输入 | 受预算约束的图谱上下文、额外符号、发送前预览及请求哈希 | 把预览、诊断和报告串成一个用户任务 |
| 云端推理 | 显式 DeepSeek 调用、JSON 输出、失败分类 | 将结果保存到同一任务中；失败也留下明确状态 |
| 证据 | 文件、行号、引文和已发送上下文校验 | 区分引文通过、问题确认和修复验证；给 issue 稳定 ID |
| 输出 | CLI 摘要和 `--json` | 直接可读的完整发现、影响、建议、状态和历史 |
| 修复 | `suggested_fix` 文本 | 用户选择 issue、记录人工处理、复查同一问题 |
| 验证 | 静态引用校验；没有修复前后测试记录 | 显式回归命令及前后结果，或明确标为未验证 |
| 交付 | `v0.1.0` 预览版 wheel、CI、公开仓库 | 把新闭环装进发行包并提供一条完整使用路径 |

近期评估还说明了诊断边界：症状提示的 V2 第一轮找到了四个已知缺陷，但修复后样本有三条已接受误报，第二轮因无效 JSON 提前停止。因此引文匹配不能被写成“缺陷已证实”，自由症状提示仍不进入默认诊断提示词。

实现按职责拆开：`repo_doctor/case.py` 管理任务数据、状态与原子保存；`repo_doctor/report.py` 生成 Markdown；`repo_doctor/verify.py` 只处理显式回归命令与结果；`repo_doctor/cli.py` 负责参数和展示。复用现有 `index.py`、`context.py`、`diagnosis.py` 和 `evidence.py`，只有具体失败证明需要时才改动 DeepSeek 传输层。对应的任务数据、报告展示、CLI 和验证测试分别放入 `tests/` 的聚焦文件。

## 3. 已交付的基本成品：v0.2.0

### 用户流程

以下是 v0.2.0 的产品入口。实现时扩展现有命令，最终文档与命令帮助都按这条连续路径组织。

```bash
repo-doctor report create REPO --out CASE_DIR
repo-doctor symbols REPO --query NAME
repo-doctor context REPO SYMBOL
repo-doctor diagnose REPO SYMBOL --preview
repo-doctor diagnose REPO SYMBOL --expect-request-sha256 HASH --case CASE_DIR
repo-doctor issue CASE_DIR ISSUE_ID
repo-doctor verify CASE_DIR ISSUE_ID --phase before -- python -m pytest tests/test_regression.py
# 用户检查建议并修改自己的仓库
repo-doctor verify CASE_DIR ISSUE_ID --phase after -- python -m pytest tests/test_regression.py
repo-doctor issue CASE_DIR ISSUE_ID --status resolved --note '已复核'
repo-doctor report show CASE_DIR
```

`report create` 建立任务，`report show` 读取已有任务；两者的路径含义明确区分。`diagnose --case` 把诊断追加到已有任务，`issue` 读取或更新人工判断，`verify` 只在用户显式调用时执行所给命令。

一个任务目录至少包含：

- `case.json`：schema 版本、工具版本、仓库修订或工作树指纹、扫描摘要、目标符号、上下文和请求哈希、模型信息、issue 列表、验证历史。
- `report.md`：人能直接阅读的仓库概况、静态观察、issue 证据与影响、建议动作、复查结果和剩余不确定性。
- 稳定 issue ID：同一任务内不可因重新排版或排序而改变；模型输出不能覆盖已有人工判断。

这些文件由用户显式指定目录保存，可能含源码引文。程序不保存 API Key 和原始服务端正文，默认扫描与报告不运行目标仓库代码、不联网。只有显式 `diagnose` 联网；只有显式 `reproduce` 或 `verify -- <argv>` 执行用户选定的本地命令。两者等同于用户在该仓库运行测试，应清楚展示命令、使用最小必要环境、移除 DeepSeek Key、限制耗时和输出，并且不能宣称提供了操作系统级隔离。

### 结果语义

每个 issue 分别记录三类状态，避免混成一个“可信分数”：

1. **来源证据**：静态分析可确定的事实、引文已校验、引文被拒绝。
2. **人工判断**：未审、确认相关、驳回、已处理；修改必须带时间和备注。
3. **回归验证**：未运行、修改前失败、修改后通过、修改后仍失败、命令失败。报告保留命令参数、退出码、耗时及有限输出摘要。

只有同一条用户指定的回归命令在修改前失败、源码发生变化、最新一轮修改后检查通过，并且用户确认测试与该 issue 相关时，报告才可写“有修复证据”。开始新的 `before` 检查后，上一轮的结论会转为“仍需复核”，历史证据仍保留；需要本轮 `after` 也满足条件才能重新闭环。模型置信度作为模型字段展示，不转换成产品可信度或健康分。

## 4. 按闭环推进的工作清单

以下任务按同一个任务目录逐步增加能力。完成一项后要能展示真实的用户动作；不要先开新的实验分支或继续堆单点分析器。

### P0-1：建立持久的仓库任务

- [x] 在现有 `scan`、`context`、`impact` 基础上定义 `case.json` v1 与 `report.md`，写入用户指定目录。先纳入确定性扫描事实：文件/符号统计、解析错误、导入环、目标符号的已解析影响路径；未解析调用只作覆盖边界，不当作缺陷。
- [x] 报告显示仓库修订、扫描时间、解析失败与省略范围。重复打开任务可读，原始证据不会被下一次诊断覆盖；写文件使用原子替换并限制权限。
- [x] 提供按名称或 ID 搜索符号的 CLI 入口，输出可直接复制到 `context` / `diagnose` 的 ID。不存在的符号给出候选，不自动选中。

**完成画面：** 用户输入仓库路径后，得到一个可保存、可重开的仓库任务，并能选中一个符号继续调查。

### P0-2：把诊断变成可处理的 issue

- [x] 将现有有界上下文、发送预览、DeepSeek 调用和证据校验接入该任务；正式发送仍需用户显式操作。成功、空发现、引文拒绝、无效 JSON 和连接失败都有明确任务状态。
- [x] 把每条 finding 保存为 issue。终端与 Markdown 报告完整显示标题、相对路径与行号、原文、推理、影响、建议、证据状态；不能只显示标题。人工确认/驳回写入同一任务，不改变原始模型输出。
- [x] `--json` 现有诊断输出继续兼容；新增任务格式有独立 `schema_version`，不让评估工具的内部记录变成用户报告格式。

**完成画面：** 用户能打开某个 issue，看懂依据与下一步，并能明确标记“这个判断不成立”。

### P0-3：记录修复与复查

- [x] 增加显式、单条 issue 的回归检查入口。命令作为参数数组运行，不经 shell；在目标仓库目录运行，设定超时和输出上限。不能因 `report`、`scan` 或 `diagnose` 自动执行目标代码。
- [x] 分别记录修改前和修改后的同一命令、退出码、源文件/仓库指纹与时间；不同命令不能自动组成“前后通过”结论。人工确认测试关联后，报告更新为“有修复证据”或“复查未通过”。
- [x] 在本项目自带的可控缺陷样例上走通失败 → 人工修改 → 同一回归命令通过 → issue 状态更新。真实外部仓库只做静态和诊断演示，不自动运行其代码。

**完成画面：** 一份报告中看得到问题来源、处理动作、修改前失败和修改后通过；缺少任何一环时明确显示未闭环。

### P0-4：把闭环交付为产品

- [x] 把 README 改成一条从安装到最终报告的实操教程，解释每个状态、API 发送范围、报告中的源码内容和显式执行测试的边界。提供一个随包可运行的小样例。
- [x] 以新增用户流程为依据更新版本到 `0.2.0`，从干净环境安装 wheel，确认任务报告、诊断和复查都能通过安装后的 `repo-doctor` 命令完成。
- [x] 复核当前未合并分支与远端默认分支的差异，把完整产品变更经 PR、CI 和版本标签交付。最终交付包含安装命令、示例任务目录、完整报告、版本/提交和已知边界。

**完成画面：** 不进入源码目录、不调用内部评估脚本，用户也能从一个 Python 仓库走完上述任务。

### v0.2.0 的完成定义

- 一个新用户可从公开版本安装 CLI，并按文档完成一次“仓库 → 目标 → issue → 人工修复 → 回归复查 → 最终报告”。
- 至少一个可控缺陷样例保存了修复前失败与修复后通过的证据；另有一个真实 Python 仓库的静态结构报告。
- 云端路径在配置好 Key 时完成一次受控请求；若服务不可用，报告明确保留失败状态，不能声称云端诊断已验收。
- 报告每条 AI 结论仍标为待人工判断；引文校验、人工确认和回归结果分别可见。
- 安装后的命令、完整项目测试和支持的 Python 版本 CI 对交付提交有效。测试是交付门槛，不代替上述用户闭环。

## 5. 成品之后的路线

### M1：诊断质量和整仓价值

- [x] 在新的修复前后样本上登记并执行质量门槛，记录真实缺陷命中、修复后误报、无效响应率和每个有用 issue 的调用成本。[M1 v2](evaluations/2026-09-29-m1-holdout-v2.md) 的六次调用命中 0/3 个已知缺陷、出现一次修复后误报和一次无效 JSON，门槛**未通过**；每个有用 issue 的成本因此不可定义。保持人工复核，不把该模型输出称为可靠缺陷发现。
- [x] 增加可确定性解释的静态分析项与优先级规则，让仓库概况能提示具体检查入口；不把未解析调用、测试文件缺失或模型分数直接叫作 bug。默认分支的报告按扫描完整性、导入关系、跨文件直接调用入口排序，均保留源码位置和检查理由；顺序不是缺陷严重度。
- [x] 增加架构与改动影响摘要：重要模块、静态依赖边界、选定符号的直接/间接影响，引用对应源码和图边。默认分支按不同生产代码依赖文件数列出最多五个模块及导入/调用边；选定符号的每一跳反向调用和直接导入者都有文件行号。它只描述已解析的静态关系，不等于运行时覆盖。
- [x] 增加用户显式运行的失败复现记录，并在选择该记录时绑定诊断预览、源码指纹、issue 和同一命令的修复后复查。它提供可追溯的真实失败入口；诊断结论仍需人工与回归验证，不把复现命令退出码直接称为根因证明。
- [ ] 找到经独立修复前后样本验证的有效诊断入口，同时控制修复后误报和无效响应；此前继续把云端诊断作为待人工判断的假设。优先利用用户明确提供的症状或复现线索，因为此前无症状的盲测多次未命中已知缺陷，症状实验虽能提高命中却仍有误报。[Pro 同上下文候选筛选](evaluations/2026-09-30-m1-pro-screen.md)虽有 6/6 可解析响应，仍命中 0/3 个已知缺陷且产生一次修复后误报，未达到进入独立样本验证的门槛；保留 Flash 默认模型。

### M2：受控补丁

- [ ] 对人工确认的一个 issue 生成补丁提案，展示精确 diff 和预期验证命令；必须在隔离工作树中应用，保留可撤销来源。
- [ ] 补丁后运行用户批准的检查，把失败/通过与对应版本绑定；只有验证证据充分才建议采纳，不自动提交、推送或合并。

### M3：扩大覆盖

- [ ] 在 Python 闭环稳定后再考虑多符号队列、整仓问答、更多语言和界面。每项先证明它提升用户完成一次调查的效率或结论质量。

## 6. 执行纪律

- 以后每项工作必须指向上面闭环的一个缺口，并有用户可见的完成画面。新的模型对照或分析器只有在解决明确阻塞时才进入当前里程碑。
- 首要代理负责范围、实现顺序、风险、最终复核与发布。只有目标、允许文件、机械步骤和验证命令都确定后，才可依照 `AGENTS.md` 把小任务交给 Luna；安全、外部请求、修复验证设计和发布不交给执行子代理判断。
- 每完成一个 P0 项，更新同一份任务样例和本指导书的勾选状态。P0 四项全部达成后交付基本成品，再开启 M1。
