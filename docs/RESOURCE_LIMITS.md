# 分析资源边界

以下边界从 1.0 开发候选开始生效；公开版本身份以 Release 为准。五个核心 JSON 和 `map.json` 的 `resource_limits` 记录实际默认值。

| 项目 | 默认上限 | 超限结果 |
| --- | --- | --- |
| 单次读取的选中实现文件 | 2 MiB = 2,097,152 原始字节 | 说明文件与 `max_file_bytes` |
| 同次分析累计源码读取 | 64 MiB = 67,108,864 原始字节 | 说明文件与 `max_total_bytes` |
| 选中实现文件数量 | 5,000 | 解析前报告 `max_files` |
| 每次 Git 子进程 | 15 秒 | 报告 `git_timeout_seconds`，不静默改用 walk |
| 索引与证据准备检查点时间 | 60 秒 | 报告 `index_timeout_seconds` 和 cooperative |
| `impact --depth` | 1–10，默认 2 | 参数错误 |

恰好到边界允许通过。整体资源超限退出 **2**，stdout 不输出成功 JSON，不创建 map、context 快照或案件目录。普通语法错误仍作为文件级覆盖缺失返回，不等于资源超限。

## 字节与时间的含义

- Python 与所选 JS/TS 共用预算；未选择的语言及非实现文件不计入源码文件数/字节。
- 按原始字节计量，不按 Unicode 字符数。编码 cookie、BOM 和 CRLF 的既有处理保留。读取最多剩余预算 +1 字节来判断超限，不先无界读取再统计。
- 累计量包含指纹和上下文的再次读取，**不是去重后的仓库磁盘大小**。例如 map 需要索引一次、指纹两次；接近 64 MiB 的仓库总量可能在准备证据时超限。每次 CLI 调查重新建立预算，不跨查询累加。
- 60 秒从索引开始，在目录/文件、解析之后、图构建阶段及证据准备边界检查。一次 native parser、系统调用或图阶段不会被强制中断；它返回后才发现超时。因此这不是硬实时保证，也不是进程 RSS 上限。最终文件写入不属于该检查点时限。
- 旧 `diagnose` 提供方请求使用原有网络 timeout；仅其等待时间从分析时钟扣除，字节预算保留。核心五步无 API 请求。
- map 的 200 节点/500 边限制属于每个可见投影，与上述分析预算不同。

## 超限后怎样继续调查

例如 `error: max_file_bytes limit 2097152 exceeded: generated/huge.py`。先定位报出的文件或范围，再选择较小的源码子目录；也可通过 `--languages` 只选择当前问题需要的语言。缩小根目录会同时缩小可见导入/影响范围，必须在调查结论中保留这一限制。不要将超限失败或空影响结果解释为没有影响。

忽略规则仍以 Git 或既有生成目录规则为准；工具不自动删除/改写目标文件、不安装目标依赖、不执行目标代码。没有提供解除全部限制的用户开关。

## 可复现的规模记录

维护者可用独立安装的 JS-extra CLI 运行：

```sh
python tools/profile_analysis.py --cli "$RD_CLI" --out "$RD_EVIDENCE/scale" --sizes 100,1000 --runs 4
```

脚本只生成自有 Python/JS/TS 静态源码，按实际搜索返回的 ID 完成 overview → symbols → context → impact → map。每个规模记录一次首次和三次重复的单命令、五步总耗时、安装环境及源码哈希，核对语法/调用/SVG 和源码不变。实验的外部子进程截止是 90 秒，与产品 cooperative 超限分开记录；超时不计成功。

本轮参考机目标为每条查询 <60 秒、五步总计 ≤120 秒。正式性能描述须引用实际生成的 `summary.json`；不能推广成所有硬件和仓库的保证。尚未运行的规模不能声称已验证。
